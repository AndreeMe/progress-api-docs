# Техническое задание: API для каталога товаров Progress NW

## 1. Общие сведения

**Проект:** Progress NW Catalog API  
**Версия ТЗ:** 1.0.0  
**Источник данных:** сайт https://progress-nw.ru/catalog  
**Назначение:** API для получения данных каталога товаров с целью создания и актуализации RAG (Retrieval Augmented Generation) системы

## 2. Назначение и цели

### 2.1. Назначение

API предназначен для предоставления программного доступа к каталогу товаров компании Progress NW с возможностью:
- Получения списка всех товаров с метаданными
- Получения полных описаний товаров в формате JSON
- Отслеживания изменений в описаниях товаров
- Фильтрации товаров по статусу (актуальный/архивный)

### 2.2. Цели

1. **Создание RAG-базы** — получение полных описаний товаров для векторизации
2. **Актуализация RAG-базы** — отслеживание изменений по дате обновления
3. **Синхронизация статусов** — получение информации об архивных товарах

## 3. Требования к API

### 3.1. Общие требования

| Параметр | Значение |
|----------|----------|
| Формат данных | JSON (UTF-8) |
| Протокол | HTTPS |
| Аутентификация | API Key в заголовке `X-API-Key` |
| Rate Limit | 100 запросов/мин |
| Базовый URL | `https://progress-nw.ru/api/v1` |
| Версионирование | Через URL (`/api/v1/`) |

### 3.2. Требования к безопасности

- Все запросы требуют валидного API Key
- API Key передаётся в заголовке `X-API-Key`
- При отсутствии или невалидности ключа — ответ `401 Unauthorized`
- При превышении rate limit — ответ `429 Too Many Requests`

## 4. Эндпоинты

### 4.1. GET /products/summary

**Назначение:** Получение списка всех товаров с датами обновления и статусами.

**Параметры запроса:**

| Параметр | Тип | Обяз. | По умолчанию | Описание |
|----------|-----|-------|--------------|----------|
| `status` | string | Нет | `active` | Фильтр по статусу: `active`, `archived`, `all` |
| `updated_from` | string (date-time) | Нет | — | Фильтр по дате обновления (ISO 8601) |
| `page` | integer | Нет | 1 | Номер страницы |
| `limit` | integer | Нет | 100 | Размер страницы (макс: 500) |

**Пример запроса:**
```http
GET /api/v1/products/summary?status=all&updated_from=2024-01-01T00:00:00Z&page=1&limit=100
X-API-Key: YOUR_API_KEY
```

**Ответ (200 OK):**
```json

      "category_slug": "ventilyatory",
      "status": "active",
      "updated_at": "2024-03-15T10:30:00Z",
      "description_updated_at": "2024-03-15T10:30:00Z"
    },
    {
      "id": "duct-round-d100",
      "name": "Воздуховод круглый D100",
      "slug": "vozduhovod-kruglyy-d100",
      "category": "Воздуховоды",
```

**Поля ответа — подробные разъяснения:**

| Поле | Тип | Что это | Зачем нужно / что было бы без него |
|------|-----|---------|-------------------------------------|
| `total` | integer | Общее количество товаров, найденных по запросу | Позволяет клиенту оценить объём данных и рассчитать количество страниц для обхода. Без него клиент не знал бы, сколько всего товаров существует, и не мог бы корректно организовать постраничную загрузку |
| `page` | integer | Номер текущей страницы (начиная с 1) | Позволяет клиенту отслеживать прогресс загрузки и запрашивать следующую страницу. Без него клиент не знал бы, какую страницу запрашивать следующей |
| `limit` | integer | Сколько товаров возвращается на одной странице | Позволяет клиенту контролировать размер ответа и нагрузку на сеть. Без него клиент не мог бы предсказать объём данных и мог бы получить слишком большой ответ |
| `pages` | integer | Общее количество страниц | Позволяет клиенту понять, сколько ещё запросов нужно сделать для полной загрузки. Без него клиент мог бы только гадать, есть ли ещё данные |
| `products` | array | Массив товаров — основной полезный груз ответа | Контейнер для списка товаров. Без него нечего было бы возвращать |
| `products[].id` | string | Уникальный идентификатор товара в системе (технический ключ, например `vent-axial-vk-315`) | Главный ключ для однозначной идентификации товара. Используется для запроса детальной информации (`GET /products/{id}`). Без него невозможно было бы сослаться на конкретный товар — при изменении имени или категории товар стало бы невозможно идентифицировать |
| `products[].name` | string | Наименование товара, как оно отображается на сайте (например, «Вентилятор осевой VK 315») | Человекочитаемое название для отображения в интерфейсе, отчётах, логах. Без него клиент видел бы только технические идентификаторы и не мог бы понять, что за товар |
| `products[].slug` | string | URL-friendly идентификатор (ЧПУ — человеко-понятный URL), например `ventilyator-osevoy-vk-315`. Состоит только из латиницы, цифр и дефисов | **Slug** — это транслитерированное название товара, используемое для формирования красивых URL. Пример: `https://progress-nw.ru/catalog/ventilyator-osevoy-vk-315` вместо `https://progress-nw.ru/catalog/?id=12345`. Нужен для SEO (поисковые системы лучше индексируют читаемые URL), для удобства пользователей (видно название в адресной строке), для формирования ссылок на карточки товаров. Без slug URL были бы вида `?id=12345` — нечитаемые, не индексируемые поисковиками, бесполезные для прямого перехода по ссылке |
| `products[].category` | string | Наименование категории товара (например, «Вентиляторы») | Позволяет быстро понять, к какой группе относится товар, без запроса детальной информации. Без него клиент не мог бы сгруппировать товары по категориям на уровне summary |
| `products[].category_slug` | string | URL-friendly идентификатор категории (например, `ventilyatory`) | Позволяет сформировать ссылку на страницу категории: `https://progress-nw.ru/catalog/ventilyatory`. Нужен для фильтрации и навигации по категориям. Без него нельзя было бы перейти к списку товаров той же категории |
| `products[].status` | string | Статус товара: `active` (актуальный, продаётся) или `archived` (снят с производства, архивный) | Критически важен для RAG — позволяет исключить архивные товары из поисковой выдачи. Без него RAG-система могла бы рекомендовать товары, которых больше нет в продаже |
| `products[].updated_at` | string (date-time) | Дата и время последнего изменения любого поля товара (цена, наличие, описание, характеристики) | Позволяет отслеживать любые изменения товара. Используется для инкрементальной синхронизации — клиент запрашивает только товары, изменённые с даты последней синхронизации. Без него пришлось бы каждый раз загружать все товары целиком |
| `products[].description_updated_at` | string (date-time) | Дата и время последнего изменения именно описания товара (текста) | Позволяет отследить, изменилось ли именно текстовое описание — это важно для RAG, так как при изменении описания нужно перевекторизовать товар. Без него RAG-система не знала бы, нужно ли обновлять вектор для конкретного товара, и либо перевекторизовала бы всё подряд (дорого), либо пропускала бы изменения |

**Коды ответов:**

| Код | Описание |
|-----|----------|
| 200 | Успешный ответ |
| 400 | Неверные параметры запроса |
| 401 | Неавторизован |
| 429 | Превышен rate limit |
| 500 | Внутренняя ошибка сервера |

#### category — Категория товара

| Поле | Тип | Обяз. | Что это | Зачем нужно / что было бы без него |
|------|-----|-------|---------|-------------------------------------|
| `category.id` | string | Да | Внутренний идентификатор категории | Нужен для программной работы с категориями — фильтрации, группировки. Без него пришлось бы искать категорию по имени, что ненадёжно (имена могут меняться, содержать опечатки) |
| `category.name` | string | Да | Наименование категории (например, «Вентиляторы») | Человекочитаемое название категории для отображения в интерфейсе. Без него пользователь не понял бы, к какой группе относится товар |
| `category.slug` | string | Да | URL-friendly идентификатор категории | Позволяет сформировать ссылку на страницу категории. Без него нельзя было бы перейти к просмотру всех товаров этой категории |
| `category.parent` | string | Нет | Идентификатор родительской категории (для вложенных категорий) | Позволяет восстановить иерархию категорий. Без него клиент не знал бы, что «Осевые вентиляторы» — это подкатегория «Вентиляторов» |

#### description — Описание товара

| Поле | Тип | Обяз. | Что это | Зачем нужно / что было бы без него |
|------|-----|-------|---------|-------------------------------------|
| `description.short` | string | Да | Краткое описание товара (1–2 предложения). Используется в карточке товара в списке, в превью | Нужно для быстрого ознакомления с товаром без чтения полного описания. Без него в списках товаров пришлось бы показывать только название или обрезать полный текст |
| `description.full` | string | Да | Полное описание товара в формате HTML (с разметкой: абзацы, списки, выделения) | Нужно для отображения на сайте с сохранением форматирования. Без него описание на странице товара было бы сплошным текстом без структуры |
| `description.plain_text` | string | Да | Полное описание товара в виде чистого текста (без HTML-тегов) | **Ключевое поле для RAG.** Используется для векторизации — преобразования текста в эмбеддинги. HTML-теги мешают векторизации, так как содержат служебную разметку, а не смысл. Без этого поля RAG-системе пришлось бы самостоятельно очищать HTML от тегов, что может привести к потере смысла или включению мусора в вектор |
| `description.updated_at` | string (date-time) | Да | Дата последнего изменения описания | Позволяет RAG-системе понять, нужно ли перевекторизовать описание. Без него пришлось бы перевекторизовать все товары при каждой синхронизации, даже если описания не менялись |

#### specifications — Технические характеристики

| Поле | Тип | Обяз. | Что это | Зачем нужно / что было бы без него |
|------|-----|-------|---------|-------------------------------------|
| `specifications` | array | Да | Массив технических характеристик товара | Содержит числовые и текстовые параметры, важные для поиска и сравнения. Без него RAG-система не знала бы технические параметры товаров |
| `specifications[].key` | string | Да | Унифицированный ключ характеристики (например, `diameter`, `airflow`, `power`) | Позволяет программно идентифицировать тип характеристики независимо от языка. Без него пришлось бы сопоставлять по тексту label, что ненадёжно |
| `specifications[].label` | string | Да | Человекочитаемое название характеристики (например, «Диаметр подключения») | Нужно для отображения в интерфейсе. Без него пользователь видел бы только технические ключи вроде `diameter` |
| `specifications[].value` | string | Да | Значение характеристики в виде строки (например, «315 мм») | Универсальное поле для любого типа значений. Без него нечего было бы показывать пользователю |
| `specifications[].value_num` | number | Нет | Числовое значение характеристики (например, `315`) | Позволяет выполнять числовые сравнения: «найти все вентиляторы производительностью > 1000 м³/ч». Без него фильтрация по числовым параметрам была бы невозможна или требовала бы парсинга строки |
| `specifications[].unit` | string | Нет | Единица измерения (например, `мм`, `м³/ч`, `Вт`) | Нужно для корректного отображения значения. Без него число `315` было бы бессмысленным — неясно, это мм, см или дюймы |
| `specifications[].group` | string | Нет | Группа характеристик (например, «Основные», «Электрические», «Акустика») | Позволяет сгруппировать характеристики при отображении. Без него все характеристики шли бы сплошным списком без структуры |

#### media — Медиа-контент

| Поле | Тип | Обяз. | Что это | Зачем нужно / что было бы без него |
|------|-----|-------|---------|-------------------------------------|
| `media` | object | Нет | Контейнер для изображений и документов | Группирует все медиа-ресурсы товара. Без него изображения и документы были бы разбросаны по корневому уровню |
| `media.images` | array | Нет | Массив изображений товара | Позволяет получить все фото товара. Без него RAG-система не могла бы использовать изображения для мультимодального поиска |
| `media.images[].url` | string | Да | URL изображения | Прямая ссылка на файл изображения. Без него невозможно загрузить изображение |

## 5. Сценарии использования

### 5.1. Первичное создание RAG-базы

```
1. GET /categories — получение дерева категорий
2. GET /products/summary?status=active&limit=500 — получение всех активных товаров (по страницам)
3. Для каждого товара: GET /products/{product_id} — получение полного описания
4. Векторизация поля description.plain_text + specifications
5. Сохранение в векторную базу данных
```

### 5.2. Инкрементальная актуализация RAG-базы

```
1. GET /products/summary?status=all&updated_from=2024-03-01T00:00:00Z
   — получение товаров, изменённых с последней синхронизации
2. Для каждого товара: GET /products/{product_id}
3. Сравнение description.updated_at с локальной копией
4. Обновление векторов для изменённых товаров
5. Удаление из индекса товаров со статусом archived
```

### 5.3. Мониторинг изменений

```
1. Периодический опрос (cron): GET /products/summary?updated_from=<last_sync>
2. При наличии изменений — запуск актуализации
3. Обновление last_sync timestamp
```

### 12.1. Модификация базы данных

### 12.2. Автоматическое обновление дат

**При изменении товара через админку:**

| Действие | Что обновляется |
|----------|-----------------|
| Изменено название, цена, наличие, категория, характеристики, фото | `updated_at` = NOW() |
| Изменено описание (short, full, plain_text) | `updated_at` = NOW() **и** `description_updated_at` = NOW() |
| Создан новый товар | `created_at` = NOW(), `updated_at` = NOW(), `description_updated_at` = NOW() |
| Товар переведён в архив | `updated_at` = NOW() (статус изменился) |
| Товар восстановлен из архива | `updated_at` = NOW() (статус изменился) |

**При импорте товаров (из 1С, Excel, CSV):**

| Сценарий | Что обновляется |
|----------|-----------------|
| Обновлена запись | `updated_at` = NOW(). Если изменилось описание — также `description_updated_at` = NOW() |
| Создана новая запись | `created_at` = NOW(), `updated_at` = NOW(), `description_updated_at` = NOW() |
| Запись не изменилась (данные совпали) | Ничего не обновляется |

### 12.3. Генерация plain_text из HTML

Если на сайте описание хранится только в HTML-формате (`full`), необходимо автоматически генерировать `plain_text`:

**Алгоритм:**
1. Удалить все HTML-теги из `full`
2. Заменить `<br>`, `<p>`, `</p>`, `<li>`, `</li>` на переносы строк
3. Убрать множественные пробелы и пустые строки
4. Обрезать до разумного предела (4000 символов для RAG)
5. Сохранить результат в `plain_text`

**Когда запускать:**
- При сохранении товара в админке
- При импорте товаров
- Одноразово для всех существующих товаров (миграция)

### 12.4. Использование существующего slug

Поле `slug` уже существует на сайте (пример: `ventiliator_kanalnyi_kruglyi_vac1_250_metallicheskiy_korpus_019_kvt_08a`).

**Что нужно сделать:**
1. Убедиться, что slug хранится в отдельном поле БД (не генерируется на лету)
2. Убедиться, что slug уникален для каждого товара
3. При создании нового товара — генерировать slug автоматически (транслитерация названия)
4. При изменении названия — **не менять** slug автоматически (чтобы не ломать старые ссылки), либо менять с редиректом

**Формат на сайте:**
- Разделитель: `_` (подчёркивание)
- Регистр: нижний
- Транслитерация: кириллица → латиница

**Решение для API:** API отдаёт slug как есть (с `_`). Если нужен формат с `-` — добавить поле `url` с полным URL страницы товара.

### 12.5. Индексы базы данных

Для обеспечения производительности API необходимо создать индексы:

| Таблица | Поля | Тип | Зачем |
|---------|------|-----|-------|
| `products` | `status` | B-tree | Фильтрация по статусу |
| `products` | `updated_at` | B-tree | Фильтрация по дате обновления (инкрементальная синхронизация) |
| `products` | `description_updated_at` | B-tree | Фильтрация по дате обновления описания |
| `products` | `slug` | UNIQUE | Быстрый поиск по slug, гарантия уникальности |
| `products` | `category_id` | B-tree | Фильтрация по категории |
| `categories` | `slug` | UNIQUE | Быстрый поиск категории по slug |
| `categories` | `parent_id` | B-tree | Построение дерева категорий |

### 12.6. API-слой

Необходимо реализовать REST API эндпоинты (описаны в разделе 4):

| Эндпоинт | Метод | Назначение |
|----------|-------|------------|
| `/api/v1/products/summary` | GET | Список товаров с датами и статусами |
| `/api/v1/products/{product_id}` | GET | Полное описание товара |
| `/api/v1/products` | GET | Пакетный режим (список с описаниями) |
| `/api/v1/categories` | GET | Дерево категорий |

**Требования к API:**
- Аутентификация через заголовок `X-API-Key`
- Rate limiting: 100 запросов/мин
- Пагинация: параметры `page`, `limit`
- Фильтрация: параметры `status`, `updated_from`
- Формат ответа: JSON (UTF-8)
- Кодировка дат: ISO 8601 (например, `2024-03-15T10:30:00Z`)

### 12.7. Миграция существующих данных

Для уже существующих товаров необходимо выполнить одноразовую миграцию:

```sql
-- 1. Заполнить created_at и updated_at текущей датой (если данных о времени создания нет)
UPDATE products SET created_at = NOW(), updated_at = NOW() WHERE created_at IS NULL;

-- 2. Заполнить description_updated_at текущей датой (если нет истории изменений описаний)
UPDATE products SET description_updated_at = NOW() WHERE description_updated_at IS NULL;

-- 3. Slug уже существует — проверить уникальность и при необходимости исправить дубликаты
SELECT slug, COUNT(*) as cnt FROM products GROUP BY slug HAVING cnt > 1;

-- 4. Сгенерировать plain_text из full для всех товаров
-- (зависит от платформы — может потребоваться скрипт)

-- 5. Создать индексы
CREATE UNIQUE INDEX idx_products_slug ON products(slug);
CREATE INDEX idx_products_updated_at ON products(updated_at);
CREATE INDEX idx_products_description_updated_at ON products(description_updated_at);
CREATE INDEX idx_products_status ON products(status);
```

### 12.8. CMS / платформа

Текущая платформа сайта не определена (данные о CMS отсутствуют в публичном доступе). Необходимо:

1. **Определить CMS/фреймворк** — Bitrix, WordPress, самописная система и т.д.
2. **Оценить возможность расширения** — можно ли добавить поля в таблицу товаров
3. **Определить механизм обновления дат** — через триггеры БД, через ORM-события, через хуки CMS
4. **Определить механизм генерации slug** — встроенный функционал CMS или кастомный код

Если текущая платформа не позволяет внести необходимые изменения — рассмотреть вариант:
- Отдельный микросервис для API, который читает из той же БД
- Отдельная витрина данных (data mart) с нужной структурой
- Промежуточная БД, синхронизируемая с основной

### 16.4. Рекомендации по снижению трудоемкости

1. **Микросервис вместо расширения CMS** — если CMS сложная, проще сделать отдельный API на FastAPI/Express, который читает из той же БД. Это изолирует изменения от основного сайта.
2. **Поэтапная поставка** — сначала `/products/summary` и `/products/{id}` (80% ценности для RAG), затем `/products` и `/categories`.
3. **Миграция данных** — если нет истории изменений, заполнить `updated_at` текущей датой для всех товаров. RAG-система при первой синхронизации загрузит всё, далее будет отслеживать изменения.
